# GenChat WebSocket Wire Protocol Specification

Version: 1.2.0  
Status: Production Standard  
Supported Transports: WebSocket (RFC 6455) over TLS 1.3  

---

## 1. Overview & Transport Handshake

GenChat client applications establish persistent real-time connections with the Edge Gateway cluster using WebSockets. The connection lifecycle enforces strict authentication, load-shedding guards, and dual-mode serialization (Binary Protocol Buffers and JSON).

### 1.1 Connection Handshake

* **Endpoint**: `GET /ws`
* **Upgrade Headers**:
  * `Authorization`: `Bearer <jwt_access_token>` (or `access_token` query parameter for constrained environments)
  * `X-Device-ID`: UUIDv4 string uniquely identifying the client device installation
  * `Sec-WebSocket-Protocol`: `chat.v1.binary` (preferred) or `chat.v1.json`

### 1.2 Handshake Rejections & Load Shedding

The gateway enforces backpressure and capacity ceilings before allocating WebSocket file descriptors:

| HTTP Status | Condition | Client Action |
|-------------|-----------|---------------|
| `401 Unauthorized` | Missing, expired, or invalid JWT signature | Refresh token via Auth service `/auth/refresh` and retry |
| `503 Service Unavailable` | Gateway pod has reached its connection ceiling (`MAX_CONNECTIONS_PER_POD`) or memory threshold | Inspect `Retry-After` header and execute exponential backoff with jitter |
| `429 Too Many Requests` | Pre-auth token-bucket IP rate limit exhausted | Wait for bucket refill interval |

## 2. Multi-Device Lifecycle & Session Eviction

GenChat accounts allow up to a configurable cap (default 5) of concurrent active devices.

### 2.1 Least-Recently-Used Device Eviction

When a user attempts to connect a 6th device:
1. The gateway registers the new device and queries the Redis presence directory.
2. The oldest device session across all gateway pods is selected for eviction.
3. The gateway delivers a graceful eviction frame before terminating the TCP socket:

```json
{
  "type": "session_evicted",
  "reason": "device_limit_exceeded",
  "max_devices": 5,
  "message": "You have been logged out because the maximum number of connected devices was exceeded on a new login."
}
```

4. The evicted client transitions to disconnected state, notifies the user with a dismissable banner, and does not automatically reconnect.

## 3. Wire Encodings

The gateway supports dual-mode frame parsing:
- **Binary Wire Format** (Primary): Protobuf messages defined in `proto/chat/v1/wire.proto`.
- **JSON Wire Format** (Fallback/Diagnostics): Strict JSON equivalents for web/debugging clients.

### 3.1 Packet Envelope

Every top-level frame exchanged over the wire encapsulates a `chat.v1.Packet`:

```protobuf
message Packet {
  string trace_id = 1;                    // W3C correlation trace ID
  google.protobuf.Timestamp sent_at = 2; // Server/Client timestamp

  oneof payload {
    ClientAction client_action = 10;
    ServerEvent server_event = 11;
    Heartbeat heartbeat = 12;
  }
}
```

## 4. Client Actions (`ClientAction`)

### 4.1 Direct Encrypted Message (`SendMessageAction`)

Clients transmit end-to-end encrypted ciphertexts generated by PQXDH (Kyber-1024 + X25519) or Double Ratchet:

```json
{
  "action": "send_message",
  "request_id": "req-uuid-1",
  "payload": {
    "conversation_id": "conv-uuid-123",
    "client_msg_id": "msg-local-id-abc",
    "encrypted_payload": "<base64_ciphertext>",
    "sender_ratchet_key": "<base64_dh_public_key>",
    "message_index": 42,
    "reply_to_message_id": "optional-parent-uuid"
  }
}
```

### 4.2 Group MLS Commit (`MlsCommitAction`)

Delivers an MLS (Messaging Layer Security) epoch transition commit to the sequencer:

```json
{
  "action": "mls_commit",
  "request_id": "req-uuid-2",
  "payload": {
    "group_id": "group-uuid-789",
    "epoch": 14,
    "commit_data": "<base64_serialized_mls_commit>"
  }
}
```

### 4.3 Delivery & Read Receipts (`AckReceiptAction`)

Acknowledges message delivery or user interaction:

```json
{
  "action": "ack_receipt",
  "payload": {
    "message_id": "msg-uuid-999",
    "conversation_id": "conv-uuid-123",
    "receipt_type": "RECEIPT_TYPE_READ"
  }
}
```

### 4.4 WebRTC & SFrame Call Signaling

Facilitates peer-to-peer and group audio/video calling secured with SFrame:

* `call_offer`: Transmits SDP offer with sender's SFrame public key.
* `call_answer`: Transmits SDP answer.
* `ice_candidate`: Transmits ICE candidate string for NAT traversal.
* `call_status`: Transitions state across `ringing`, `answered`, `rejected`, `ended`.

## 5. Server Events (`ServerEvent`)

### 5.1 Push Delivery (`InboundMessage`)

Delivered in real-time to active recipient sockets:

```json
{
  "type": "inbound_message",
  "payload": {
    "server_msg_id": "msg-srv-789",
    "client_msg_id": "msg-local-id-abc",
    "conversation_id": "conv-uuid-123",
    "sender_id": "usr-uuid-alice",
    "encrypted_payload": "<base64_ciphertext>",
    "sender_ratchet_key": "<base64_dh_public_key>",
    "sequence_number": 10452,
    "created_at": 1726700000
  }
}
```

### 5.2 Push Deduplication across Cluster Nodes

When a recipient is online on another gateway pod:
1. The origin pod publishes the payload to Redis channel `cluster:gw:{target_pod_id}`.
2. The owning pod receives the event and sends it directly down the recipient's WebSocket.
3. The presence directory lookup confirms the user is active, preventing duplicate push notifications through APNs/FCM.

---

## 6. Heartbeats & Keep-Alive

* **Ping Interval**: Client sends `Heartbeat` packet every 25 seconds.
* **Timeout Threshold**: Gateway terminates idle sockets after 60 seconds of silence.
* **Server Heartbeat**: Gateway responds with echo sequence number or standard WebSocket `PONG` frame.
